> 这是一篇示例文章。内容用于展示博客模板，不代表站主已经完成的具体研究项目。

“我记得当时能跑”不是可复现性。真正有用的实验记录，需要让另一个人在合理时间内回答三个问题：运行了什么、为什么这样运行、结果应该如何解释。

## 最小记录单元

每次正式运行至少保存下面这些信息：

- 代码版本，例如 Git commit；
- 完整配置，而不是只保存与默认值不同的字段；
- 数据版本和预处理方式；
- 随机种子、硬件与关键依赖版本；
- 原始指标、聚合方式和最终结论。

这些信息不一定全部写在一份 Markdown 中。配置可以是 YAML，指标可以是 JSONL，图表可以由脚本生成。关键是它们共享一个稳定的运行标识，并能彼此追溯。

## 区分产物与结论

实验目录适合保存机器可读的产物，研究日志适合保存人的判断。两者承担不同职责：

| 内容 | 更合适的位置 |
| --- | --- |
| 超参数、环境版本 | 运行配置 |
| 逐步指标、模型文件 | 实验产物目录 |
| 图表生成逻辑 | 版本控制中的脚本 |
| 异常解释、后续决策 | 研究日志 |

不要手工复制图表中的数字到多个地方。尽量让汇总表和图片直接从原始结果生成，减少来源不一致。

## 让失败也可搜索

失败实验经常被随手删除，但它们可能包含最有价值的边界信息。记录失败时，不需要写成长篇复盘，只要保留结构化的最小信息：

```yaml
status: failed
stage: training
reason: out_of_memory
action: reduce_batch_and_retry
```

当同类问题再次出现时，这些记录能帮助判断它是偶发故障、资源限制，还是方法本身的不稳定。

## 复现检查

在把一次结果写进论文或公开文章前，可以做一次简短检查：

1. 从干净环境重新安装依赖；
2. 仅根据保存的配置运行关键实验；
3. 用同一脚本生成汇总数字和图表；
4. 检查文字中的每个数字能否追溯到原始结果；
5. 标记无法公开的数据、权重或外部服务。

复现并不要求每次得到完全相同的浮点数。它要求变化范围已被理解，结论不会依赖一个无法解释的偶然运行。
